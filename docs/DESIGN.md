# 테슬라 차량용 노래방 시스템 — 설계 정리

## 1. 개요
테슬라 차량 안에서 쓰는 노래방 시스템. 호스트 안드로이드 폰 1대로 모든 기능이 동작하며, 별도 서버는 두지 않는다.
- 유튜브의 TJ·금영 노래방 영상만 검색·재생
- 동승자들이 각자 폰으로 QR 접속해 곡 예약·취소·예약현황 확인
- 영상은 유튜브 프리미엄 계정으로 광고 없이 재생

## 2. 사용 환경 (전제)
- 호스트 폰: 안드로이드. **Tesor** 앱으로 폰 화면을 테슬라 브라우저에 띄움
- 호스트 폰 핫스팟은 항상 켜져 있음 (테슬라 차량이 이 핫스팟에 연결)
- 동승자는 호스트 핫스팟 와이파이에 접속해서 사용 (핫스팟 경유로 인터넷도 사용)
- 목소리: 별도 블루투스 노래방 마이크 사용 (마이크 자체 스피커 + 에코 조절). **앱은 음성을 다루지 않음**
- 반주: 폰 → 블루투스 → 차량 스피커
- 호스트는 유튜브 프리미엄 가입자이며, 폰 크롬에 해당 계정으로 로그인되어 있음

## 3. 확정된 결정과 근거 (폐기안 포함 — 재제안하지 말 것)
| 방안 | 결과 | 근거 |
|---|---|---|
| 앱 내부 WebView에 유튜브 임베드 | 폐기 | 구글이 WebView 로그인을 막아 프리미엄 적용 불가 → 광고 노출 |
| 유튜브 재생목록 API로 예약 관리 + 유튜브 앱 재생 | 폐기 | 실측 결과, 유튜브 앱이 재생 중 추가된 곡을 반영하지 않음 |
| 유튜브 앱으로 곡별 호출 + 미디어세션 감시로 종료 감지 | 보류(백업안) | 동작은 가능하나 앱 전환이 보이고 구현이 까다로움 |
| 크롬에서 로컬 플레이어 페이지 + YouTube IFrame Player API | **보조(선택)** — 초기 채택 | 크롬의 프리미엄 로그인이 임베드에도 적용됨을 실측 확인 (developers.google.com 플레이어 데모에서 프리미엄 표시 확인). 재생 순서를 앱이 완전히 제어 |
| **유튜브 앱으로 곡별 재생 + 미디어 세션으로 종료 감지·제어, 예약 순서는 앱이 관리** | **채택 (2026-09-29, 기본값)** | 실사용에서 TJ 영상 다수가 "권리자가 외부 사이트·앱 재생 차단"(IFrame 오류 150)으로 확인됨 — Data API `embeddable`로는 미리 알 수 없고 프리미엄으로도 안 풀림. 유튜브 앱 안 재생은 제한 없음. 예약 목록은 앱이 쥐고 차례가 된 곡 하나만 유튜브 앱에 넘기므로, 폐기한 '재생목록 API' 방식의 문제(추가곡 미반영)가 없음. 설정에서 크롬 플레이어로 전환 가능 |
| 집 서버 사용 | 불필요 | 동승자가 핫스팟에 붙으므로 호스트 폰의 로컬 서버로 충분. 곡 DB도 폰 내부에서 처리 |

## 4. 아키텍처
```
[호스트 안드로이드 앱]
 ├─ 포그라운드 서비스
 │   ├─ 로컬 HTTP + WebSocket 서버
 │   ├─ SQLite 곡 DB (+ FTS 검색)
 │   └─ 채널 동기화 작업 (YouTube Data API v3)
 └─ 설정 화면 (핫스팟 SSID/비밀번호, API 키, 동기화 실행)

[플레이어 페이지 /player]  ← 호스트 폰 "크롬"에서 열기 → Tesor로 차 화면 표시
[동승자 페이지 /guest]      ← 동승자 폰 브라우저에서 QR로 접속
```

### 4.1 플레이어 페이지 (/player)
- 로컬 서버가 제공, **반드시 호스트 폰의 크롬에서 열기** (WebView·시크릿 모드 불가)
- YouTube IFrame Player API로 재생. WebSocket으로 서버의 큐를 받음
- `onStateChange`의 ENDED → 서버에 통보 → 다음 예약곡 `loadVideoById`
- `onError` 처리: 100(없음/비공개), 101·150(임베드 불가) 등은 자동 스킵 후 해당 곡을 DB에서 재생불가로 표시
- 화면 구성: 재생 영상(최대 크기), 다음 예약곡 목록 오버레이, QR 코드 2개(아래 4.4)
- 호스트 조작: 일시정지/재생, 스킵, 순서 변경, 삭제 (플레이어 페이지 또는 호스트 앱 중 위치는 구현 시 결정)

### 4.2 동승자 페이지 (/guest)
- 설치 없이 브라우저로 사용. 링크 입력 없이 곡 DB 검색 → 탭으로 예약
- 기능: 곡 검색, 예약, 예약현황 실시간 확인, **본인 예약만** 취소
- 큐는 전원이 함께 보는 하나의 목록 (예약자 닉네임 표시, 내 예약 강조)
- 검색 결과는 **곡 단위로 묶어** 한 줄씩 표시 (정규화한 곡명+가수 기준). 탭하면 기본 버전 예약, "다른 버전"에서 브랜드·여자키·남자키·멜로디제거·MR Live 선택 (결정)
  - 기본 버전 = 선호 브랜드의 기본 반주, 없으면 다른 브랜드의 기본 반주. **선호 브랜드는 호스트 앱 설정** (기본값 KY) (결정)
- **실측: TJ 영상 다수가 "TJ에서 외부 사이트·앱 재생 차단"(오류 150)** — https 페이지에서도 동일, 유튜브 앱에선 재생됨. Data API `embeddable`에는 안 드러남
  - 대응: 브랜드별 사용 켜기/끄기 설정. **기본값 TJ 끔** (검색·대체 후보·동기화에서 제외, 데이터는 유지) (결정)
  - 재생 오류 시 같은 곡의 다른 버전으로 자동 대체 (같은 버전 > 기본 반주 > 다른 브랜드), 막힌 영상은 검색에서 제외
  - 두 회사 표기가 다른 곡(영문 병기·피처링 등)은 따로 나올 수 있음 → 동기화 후 실데이터로 묶기 규칙 조정
- 재생 순서: **예약한 시간 순** (결정)
- 대기 중인 곡 취소: 예약자 본인 + 호스트. 재생 중인 곡 스킵: **예약자 본인 + 호스트** (결정). 순서 변경: 호스트만
- 첫 접속 시 닉네임 입력, 세션 ID를 쿠키로 저장해 예약 소유자 식별
- 큐 변경은 WebSocket으로 모든 접속자에게 즉시 반영

### 4.3 곡 DB와 동기화
- YouTube Data API v3, **API 키만 사용 (OAuth 불필요)**. 키는 안드로이드 앱 패키지 + SHA-1로 제한
- `search.list`는 사용하지 않음 (호출당 100유닛, 하루 기본 한도 10,000유닛)
- 동기화 절차
  1. `channels.list`로 채널의 업로드 재생목록 ID 조회
  2. `playlistItems.list`로 영상 목록 수집 (50개당 1유닛)
  3. `videos.list`(part=status,contentDetails)로 임베드 가능 여부·길이 수집 (50개당 1유닛)
  4. 최초 1회 전체 동기화, 이후엔 이미 저장된 영상을 만날 때까지만 증분 동기화
- 필터링 엔진
  - **채널 화이트리스트**: TJ미디어·금영 공식 채널 (채널 ID는 구현 시 확인). 채널 추가는 화이트리스트에 등록만 하면 되도록 설계
  - 쇼츠 등 짧은 영상 제외 (길이 기준)
  - `status.embeddable == false` 제외
  - 채널 내 비노래방 영상(홍보 등)은 제목 패턴으로 제외
- 제목 파싱으로 곡명·가수·노래방 번호·버전 추출 (`TitleParser.kt`, 형식이 안 맞으면 비노래방 영상으로 보고 제외)
  - TJ (`UCZUhx8ClCv6paFW7qi3qljg`): `[TJ노래방 / 여자키] 곡명 - 가수 / TJ Karaoke`, 번호는 설명란 `TJ 노래방 곡번호.328`
  - 금영 (`UCDqaUIUSJP5EVMEI178Zfag`): `[멜로디제거] 곡명 - 가수 (KY.84784) / KY KARAOKE`
  - 버전(여자키·남자키·멜로디제거·MR Live)은 별도 컬럼. 검색 결과에서 기본 반주를 먼저 표시
- 검색: FTS 대신 정규화 키(소문자, 공백·기호 제거)에 LIKE 부분일치 + 초성 검색
  - 검색 대상 선택: 전체 / 제목 / 가수 (각각 초성 가능). DB v3에서 artist_key, title_chosung, artist_chosung 추가
  - 근거: FTS4 기본 토크나이저는 한국어 부분일치·띄어쓰기 차이("당신만을사랑해")를 처리하지 못함. 채널 합계 약 10만 행이라 전체 스캔도 충분히 빠름
- 동기화는 페이지마다 pageToken을 저장해 중단(할당량 초과 등) 후 이어서 진행
- **빈틈 메우기 (결정)**: 목록 API 한계로 빠진 곡(예: TJ 2015년 '사랑은...하나다 - 테이')은 필요할 때만 직접 찾는다
  - "유튜브에서 더 찾기": 켜진 브랜드 채널 안에서 `search.list` (브랜드당 100유닛), **하루 30회 제한**. 찾은 곡은 DB에 저장 → 이후 로컬 검색. 동승자 페이지·호스트 패널 모두
  - "유튜브 링크로 추가" (호스트 패널): `videos.list` 1유닛, TJ·금영 채널 영상만
  - 원래 결정(search.list 미사용)의 예외: 전체 동기화에는 여전히 쓰지 않음
- **실측: API가 재생목록을 약 2만 개까지만 반환** (TJ 전체 74,700개 중 최신 2만 개 → 19,205곡, KY 19,363곡)
  - 대응: 채널마다 최신 업로드(`UU…`, 증분) + 인기 영상 자동 재생목록(`UULP…`, 30일마다 재스캔)을 합침 → 최신 2만 + 인기 2만
  - `UULP`는 비공식 자동 재생목록이라 사라질 수 있음 → 없으면 건너뜀
  - v1.0.5~6 실측: TJ 19,404곡, KY 19,382곡으로 거의 늘지 않음 → API에서 `UULP`가 안 되는 것으로 추정
  - 채널이 만든 재생목록 전체(playlists.list)도 30일마다 훑음. 다른 채널 영상(`videoOwnerChannelId`)은 제외
  - 동기화 완료 메시지에 목록별 결과(확인 개수, 새 곡 수, 실패 이유)를 표시해 어느 경로가 효과 있는지 확인
- API 키 안드로이드 앱 제한 → 요청마다 `X-Android-Package`, `X-Android-Cert`(서명 SHA-1) 헤더 전송

### 4.4 네트워크와 QR
- 앱 실행 시 핫스팟 인터페이스의 IP를 조회해 사용 (안드로이드 11+는 핫스팟 서브넷이 고정이 아님)
- ~~QR 1: 핫스팟 접속용 와이파이 QR~~ → **폐기** (동승자는 이미 핫스팟에 접속해 본 사람들이라 불필요. QR 하나로 와이파이 연결과 링크 열기를 동시에 할 수는 없음)
- QR: 동승자 페이지 주소 `http://<핫스팟IP>:<PORT>/guest?room=<토큰>`
  - 방 토큰은 **고정** (앱에 저장, 호스트 앱 "동승자 주소 초기화"로만 변경) — 루틴으로 매번 켜고 꺼도 주소 유지. 핫스팟 비밀번호를 알아야 접속 가능하므로 위험 낮음 (결정)
  - 핫스팟 IP는 바뀔 수 있어 플레이어 화면 QR은 30초마다 현재 IP로 갱신 (`/api/join-info`, `/qr/guest.svg`, 호스트 토큰 필요)
  - 대기 중엔 QR 크게(화면 아래 가운데), 노래 중엔 왼쪽 위 작게. 호스트 패널에서 숨기기 가능
  - 앱 재시작으로 세션이 사라지면 동승자 페이지가 저장된 닉네임으로 자동 재접속
  - QR 생성: ZXing core → SVG

## 5. 데이터 모델
- **Song** (SQLite): videoId(PK), channelId, rawTitle, title, artist, karaokeNo, variant, durationSec, embeddable, playable, publishedAt, 검색 키
- **QueueItem** (메모리): id, videoId, title, artist, brand, karaokeNo, variant, durationSec, ownerId(예약자 공개 ID, 호스트는 `host`), nickname, addedAt
- **GuestSession** (메모리): secret(본인 브라우저만 앎), publicId(다른 사람에게 보이는 ID), nickname
- 토큰: hostToken(앱에 영구 저장, 플레이어 페이지만 앎), roomToken(앱 프로세스 시작마다 새로 발급, 동승자 주소/QR)
  - 같은 폰 크롬에서 플레이어와 동승자 페이지를 함께 열어도 역할이 섞이지 않도록 IP가 아닌 토큰으로 구분

## 6. 로컬 API
인증 헤더: `X-Host`(호스트 토큰), `X-Room`(방 토큰), `X-Session`(동승자 세션 secret)
- `POST /api/session` {nickname} (방 토큰) → {secret, publicId, nickname}
- `GET|POST /api/me` — 내 정보 / 닉네임 변경 (내 예약의 표시 이름도 변경)
- `GET  /api/search?q=` (방 토큰) — 곡 단위로 묶인 결과 [{title, artist, versions[]}]
- `GET  /api/queue` — 예약 현황
- `POST /api/queue` {videoId} — 예약 (곡 DB에 있는 곡만)
- `DELETE /api/queue/{id}` — 대기곡 취소 (본인·호스트)
- `POST /api/queue/{id}/move?delta=` — 순서 변경 (호스트)
- `POST /api/player/{play|pause|skip|seekBy|seekTo}?seconds=` — 재생 중인 곡의 예약자 본인·호스트
- WebSocket `/ws` (플레이어는 `?host=<토큰>`)
  - 서버→전체: `state`(nowPlaying, queue), `progress`(itemId, position, duration, playing)
  - 서버→플레이어만: `command`(action, seconds)
  - 플레이어→서버 (호스트 소켓만 인정): `ended`, `error`, `progress`(5초마다 + 상태 변화 시), `skip`
- 동승자 페이지 진행 바: 마지막 보고 위치 + 경과 시간으로 로컬 보간. 대기 시간 = 현재 곡 남은 시간 + 앞 곡들 길이 합
- 테스트: 호스트 앱의 "게스트1/2로 열기" → `127.0.0.1` + `&profile=N` (profile별로 저장소를 분리해 한 폰에서 여러 동승자 흉내)

## 7. 제약과 주의사항
- 유튜브 약관: 공식 IFrame 플레이어만 사용, 광고 차단·건너뛰기 조작·다운로드 금지 (위반 시 API 키 차단 위험)
- 크롬 설정에서 서드파티 쿠키를 차단하거나 시크릿 모드로 열면 프리미엄이 풀려 광고가 나올 수 있음
- 크롬 자동재생 정책: 소리 있는 자동재생에는 사용자 조작이 필요할 수 있음 → 첫 곡은 탭으로 시작하고, 이후엔 같은 페이지를 유지하며 `loadVideoById`로 전환
- 로컬 IP의 http 페이지는 secure context가 아니라 Wake Lock 등 일부 웹 API 사용 불가 → 화면 꺼짐 방지는 Tesor/앱 쪽에서 처리 여부 확인
- 로컬 서버는 앱이 꺼지면 중단되므로 포그라운드 서비스로 유지

## 8. 개발 환경과 빌드
- **빌드는 GitHub Actions에서만 수행** (로컬 빌드 환경 없음. CLI는 코드 작성·푸시·빌드 실행/확인 담당)
- 러너: `ubuntu-latest` (안드로이드 SDK 기본 포함), JDK는 `actions/setup-java`로 설정, Gradle로 release APK 빌드
- 플레이어·동승자 페이지는 앱 `assets`에 포함되는 정적 파일 → 별도 웹 빌드 단계 없음
- **서명 키 고정 (필수)**
  - 러너의 디버그 키는 매번 새로 생성되므로 사용 금지
  - 릴리스 키스토어를 1회 생성해 base64로 GitHub Secrets에 저장 (키스토어, 비밀번호, 키 별칭, 키 비밀번호)
  - 워크플로에서 Secrets로 키스토어를 복원해 서명
  - 이유: 서명이 바뀌면 업데이트 설치가 거부되고, API 키의 SHA-1 제한도 깨짐
- **버전**: `versionCode` = `github.run_number`, `versionName` = `1.0.<run_number>` 형식으로 자동 증가
- **배포**: 빌드 완료 시 GitHub **Releases**에 태그(`v1.0.<run_number>`)와 함께 APK 업로드
  - Actions 아티팩트는 로그인 필요 + 보관기간 만료가 있어 앱 업데이트 경로로 부적합
  - 저장소는 공개 권장 (비공개면 앱에 읽기 전용 토큰 필요)
- YouTube API 키는 빌드에 포함하지 않음 → 앱 설정 화면에서 입력 (저장소·Secrets에 키 불필요)
- CLI 작업 흐름 예시: 푸시 → `gh run watch`로 빌드 대기 → `gh release download`로 APK 수령 → 호스트 폰에 설치

## 9. 앱 자동 업데이트
- 최초 1회는 사용자가 APK를 수동 설치. 이후 업데이트는 앱이 처리
- **확인**: 앱 실행 시 GitHub API `GET /repos/{owner}/{repo}/releases/latest` 조회 → 릴리스의 버전 번호와 현재 `versionCode` 비교
  - 비인증 API는 IP당 시간당 60회 제한 → 실행 시 1회 확인이면 충분
- **알림**: 새 버전이 있으면 앱 내 알림(버전, 릴리스 노트) 표시
- **진행**: 사용자가 누르면 APK를 앱 캐시에 다운로드 → PackageInstaller 세션 API로 설치 요청
  - `REQUEST_INSTALL_PACKAGES` 권한 필요, 최초 1회 "출처를 알 수 없는 앱 설치 허용" 안내 화면 연결
  - 업데이트마다 시스템 설치 확인 화면이 뜨는 것을 기본으로 가정
- **시점 제한**: 업데이트 시 앱이 재시작되어 로컬 서버와 예약 목록이 끊김
  - 예약 큐가 비어 있지 않거나 재생 중이면 알림만 표시하고 설치는 사용자가 원할 때 진행
- 서명 키 고정(8장)이 전제. 서명이 다른 APK는 설치 단계에서 거부됨
- 구현: `Updater.kt` (태그 `v1.0.N`의 N = versionCode 비교). 릴리스 노트는 워크플로가 이전 태그 이후 커밋 제목으로 생성 → 앱 알림에 표시
- 호스트 앱 상단에 업데이트 상태·버튼. 재생 중·예약 있음·동기화 중이면 설치 전 확인창

## 10. 결정 사항 / 미정 사항
- 개발 스택: **Kotlin + Ktor(CIO, WebSocket) + SQLite(SQLiteOpenHelper)** (결정, 검색 방식은 4.3)
- 패키지명: `com.guom.karaoke` (결정)
- 서명 키: PKCS12 키스토어를 openssl로 생성해 GitHub Secrets에 등록 (결정)
- TJ·금영 공식 채널 ID: 4.3 참고 (확인). 채널 내 임베드 허용 비율은 첫 동기화 후 확인 (미정)
- 호스트 조작 UI 위치: **플레이어 페이지의 호스트 패널** (결정). 차 화면에서 🔍 예약 → 검색·예약·순서 변경·삭제·재생 제어. 혼자 쓸 때도 앱 전환 없이 사용. 호스트 앱은 설정·동기화용
- 자동 활성화/대기 (4단계에서 설정 기본값 끔으로 구현 예정, 신호 미정)
  - 핫스팟 신호: WIFI_AP_STATE_CHANGED 는 실행 중인 앱만 받음 → 부팅 시 시작하는 경량 감시 서비스(상시 알림)가 켜짐/꺼짐에 따라 서버 시작/정지
  - 차 블루투스 신호: ACL_CONNECTED/DISCONNECTED 는 꺼진 앱도 깨울 수 있음 → 감시 서비스 불필요. 핫스팟이 항상 켜져 있다면 이쪽이 더 정확
  - 대안: 삼성 모드 및 루틴으로 앱 실행 + 앱에 "대기 모드" 버튼
  - **결정: 빅스비 루틴 "핫스팟 켜짐 → 앱 열기: 차량 노래방" + 서버가 핫스팟 꺼짐을 감지해 자동 종료** (설정, 기본 켬)
    - 서비스가 10초마다 핫스팟 인터페이스(swlan/ap/softap)를 확인, 켜진 걸 본 뒤 2회 연속 없으면 종료 → 와이파이로 테스트할 땐 꺼지지 않음
    - 핫스팟 꺼짐 자동 종료는 **서버만** 끈다 (알림은 유지)
  - **앱 구성 (결정)**: 앱 아이콘 = 상시 알림 띄우기 (첫 설정 전엔 설정 화면). 알림 버튼 3개
    - **실행**: 서버 켜고 크롬 플레이어 열기 (Android 12+ 알림 트램펄린 제한 때문에 투명 RunActivity 경유)
    - **종료**: 서버만 끄기 (알림 유지, 다시 실행 가능) · **설정**: 설정 화면
    - 알림 제목에 서버 상태, 새 버전 있으면 문구 표시. 알림까지 없애기 = 설정의 "앱 완전 종료"
  - 앱 화면은 설정 하나뿐 (서버 상태·동승자 주소·실행/서버 종료/앱 완전 종료·업데이트·곡 DB·브랜드·자동 종료·배터리·재생 오류). 예약 관리·검색은 플레이어의 호스트 패널
  - 크롬 탭은 `Browser.EXTRA_APPLICATION_ID`로 이 앱이 연 탭을 재사용 (탭이 쌓이지 않음, 대신 다시 열면 새로고침)
    - (폐기) 앱 목록에 "노래방 시작/종료" 아이콘을 따로 두는 방식 — 아이콘 3개로 지저분해짐
  - 평소 사용: 앱은 백그라운드 서버만, 플레이어는 크롬 즐겨찾기 `http://127.0.0.1:8080/player` (호스트 토큰은 앱 버튼으로 처음 한 번 열 때 저장)

## 12. 유튜브 앱 재생 방식 (2026-09-29~)
- 차례가 된 곡: `https://www.youtube.com/watch?v=<ID>` 인텐트를 유튜브 앱 패키지로 연다
- `MediaListenerService`(알림 접근 권한)로 `MediaSessionManager.getActiveSessions()` → 유튜브 앱 `MediaController`
  - 1초마다: 곡을 연 뒤 제목이 바뀌고 재생 중이면 "우리 곡"으로 확인 → 진행 상황 보고
  - 끝 근처(길이-2초)에서 멈춤/정지, 또는 제목이 바뀜(자동재생) → 다음 곡. 30초 안에 시작 안 되면 건너뜀
  - 일시정지·재생·이동 명령은 `transportControls`로 전달. 예약이 비면 일시정지
- 백그라운드에서 유튜브 앱을 열기 위해 "다른 앱 위에 표시" 권한 + 떠 있는 오버레이 창(다음 곡·예약 QR, 터치 통과) 필요 (Android 15+)
- 호스트 예약·관리: 알림의 "실행" → 호스트 리모컨(`/guest?host=<토큰>`, 동승자 페이지를 호스트 권한으로). 이 방식에선 `/player`는 리모컨으로 리다이렉트
- **재생 중 예약 (혼자 쓸 때)**: 오버레이 작은 창의 🔍 예약 → 화면 오른쪽 약 45%에 리모컨 패널(오버레이 창 안 WebView로 호스트 리모컨 페이지). 왼쪽에선 유튜브 영상 계속 재생, 패널 밖 터치는 유튜브로, 키보드 입력 가능. WebView에는 우리 페이지만 띄우므로 폐기한 'WebView 유튜브 임베드'와 다름. 루프백(127.0.0.1)만 평문 HTTP 허용
- 호스트가 할 일: 알림 접근·다른 앱 위에 표시 권한 허용, 유튜브 앱 자동재생 끄기
